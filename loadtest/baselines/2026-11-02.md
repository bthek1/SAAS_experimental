# Load-test baseline: 2026-11-02

**Summary.** On four Proxmox LXC containers, the API's capacity under a realistic mixed
read/write workload went from **~86 req/s** (2 gunicorn workers, a DB connection per request,
unpaginated lists) to **~274 req/s** with three changes: 5 workers, persistent DB connections,
and paginated lists. The tuned deploy **held ~215 req/s for 10 minutes with p95 19 ms and 0
errors**. The baseline never saturated CPU or Postgres. It ran out of gunicorn worker concurrency.

| | Baseline | Tuned |
|---|---|---|
| Max sustained (stress knee) | ~86 req/s | ~274 req/s (3.2×) |
| 10-minute hold | could not hold ~65 req/s* | 215 req/s, p95 19 ms, max 156 ms, 0 failed, 0 dropped |
| saas-db CPU at ~75 req/s | ~26 % | ~4 % |
| First limit | 2 sync workers (queueing) | Not worker slots: see [2026-11-03.md](2026-11-03.md) |

\* Unreset data that grew during the run; see Findings.

Plan: #9 (Phases 5–6). Pagination: #10. Raw summaries: `loadtest/results/<testid>.json` (gitignored);
per-minute tables: `just k6-report <testid>`.

## Setup

**Deploy:** four unprivileged LXC containers on the Proxmox host `192.168.2.70` (24 cores, 63 GB),
created by `infra/pulumi`, configured by `infra/ansible`:

| Container | IP | Cores | Memory | Runs |
|---|---|---|---|---|
| saas-app (241) | 192.168.2.241 | 2 | 2 GB | gunicorn (sync workers), `core.settings.loadtest`, Python 3.14 |
| saas-db (242) | 192.168.2.242 | 2 | 1 GB | Postgres 16 (`shared_buffers` 256 MB) |
| saas-monitor (243) | 192.168.2.243 | 1 | 1 GB | Prometheus 3.15.0, Grafana 13.0.9 |
| saas-loadgen (244) | 192.168.2.244 | 2 | 1 GB | k6 2.3.0 |

- **Code:** commit `b63e348` plus the uncommitted #9/#10 working tree at the time of each run.
- **Data:** every measured run starts from `just loadtest-reset`: 20 owners × 200 questionnaires
  = **4,000 questionnaires, 2,782 submitted**, 200 batteries, 60 types. Runs add rows (see Traffic).
- **Traffic** (`loadtest/k6/lib/api.js`, `mixed`), one action per iteration, ~1.6 requests each:
  50 % owner read (lists, detail, dashboard, scores), 30 % respondent flow (create → open share
  link → **submit**), 15 % battery create, 5 % health. About 47 % of requests write.
- **Stress:** `just k6 stress TARGET=lxc STEP=10 STEP_TIME=1m`: +10 iterations/s (~16 req/s)
  every minute until p95 > 1 s, failures > 1 % or 1,000 dropped iterations (k6 out of VUs).
- **Knee:** the last minute with 0 dropped iterations and worst-group p95 under ~150 ms.
- Host CPU per container comes from each container's cgroup, not node_exporter (an LXC's
  `/proc/stat` counts the host's work on its cores).

## What saturates first (baseline)

**gunicorn's worker pool, not CPU or Postgres.** At the baseline knee the two sync workers spent
~1.6 of every 2 worker-seconds inside Django views (`django_http_requests_latency_seconds_by_view_method_sum`),
while saas-app CPU was ~40 % and saas-db ~31 %. Each worker serves one request at a time and
spends much of it waiting on network round trips to saas-db, which is not CPU. Requests then
queue in the listen backlog. Django never sees that wait (it times a request from when a worker
picks it up), so Django's p95 stays under 70 ms while clients see seconds.

Where worker time went at the baseline knee:

| View | Share of worker time | Mean per request |
|---|---|---|
| `questionnaire-list` (unpaginated) | 27 % | 25.5 ms |
| `battery-list` (unpaginated) | 14 % | 23.9 ms |
| `questionnaire-submit` | 11 % | 14.1 ms |
| `questionnaire-by-token` | 8 % | |
| `dashboard` | 6 % | 23.2 ms |
| `token` (login) | 6 % | **123.9 ms** (PBKDF2, by design) |

Logins are expensive on purpose. Under queueing, k6 starts fresh VUs and each one logs in, which
adds load right when there is least room. That makes the break sharp; real users log in once.

## Findings along the way

- **Runs must start from the same data.** An early load run (`load-20261102T042847Z`, 40
  iterations/s for 10 minutes, starting from leftovers of earlier runs) grew the table from
  14,221 to 29,155 questionnaires. Because the questionnaire list was unpaginated, Django p95 crept
  from 53 to 159 ms and the run could not hold ~65 req/s (p95 2.8 s, 944 dropped iterations).
  Hence `just loadtest-reset` before every measured run. An earlier stress run on unreset data
  (`stress-20261102T042124Z`, knee ~80 req/s) is superseded by the fixed-data runs above.
- **Postgres connections read ~0** with `CONN_MAX_AGE=0`: each request opens, authenticates
  (SCRAM) and closes its own connection, so a 5 s sample rarely sees one open.
- k6's `k6_vus` series is not usable for arrival-rate scenarios; dropped iterations are the
  signal that k6 could not keep the rate.
