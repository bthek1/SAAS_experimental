# Load-test baseline: 2026-11-03, gthread workers

**Summary.** Giving each of the 5 gunicorn workers 4 threads did **not** raise capacity: the knee
is ~264 req/s, against ~274 req/s with sync workers, which is the same within run-to-run noise.
Both runs broke in minute 18. Worker slots were not the limit, which corrects what
[2026-11-02.md](2026-11-02.md) concluded.

Same setup, data reset and stress settings as 2026-11-02 (`just k6 stress TARGET=lxc STEP=10
STEP_TIME=1m`, here with `MAX_RATE=500` so the scenario's cap could not end the run). The only
change is in the gunicorn command: `--worker-class gthread --threads 4`.

## What this shows

- **Slots were not full.** Before the break, time inside Django (the sum of request durations per
  second) was 2.2 to 6.3 s/s with 20 slots, and 1.8 to 3.0 s/s with the 5 sync slots. k6 had 1 to
  19 VUs in flight. The extra threads had little to do.
- **Threads moved the wait rather than removing it.** Time inside Django rose, with Django p95 and
  p99 worse at the same rate and client latency unchanged. A likely cause is threads contending
  for each process's GIL, where they used to wait in the listen backlog. This was not measured
  directly.
- **The break is a runaway, and k6 logins are part of it.** Logins are 0/s until k6 needs more than
  its 50 pre-allocated VUs. Every extra VU then logs in (PBKDF2, ~124 ms) and fetches three lists
  of 100 rows. In the run's last 30 s, VUs went from 19 to 87 to 300 and logins reached 4.2/s, so
  the knee may be partly a test artefact. Real users rarely all log in during a slowdown.
- **What starts it: data growth in the dashboard** (next section).

## Data growth: the dashboard reads the whole table

Measured one request at a time on a throwaway local Postgres 16 (same schema, no cache), so the
milliseconds are not the sandbox's, but the ratios are comparable. Median of 20 requests:

| Endpoint | Fresh: table 4,000, owner 200 | Only other owners grew: table 55,281, owner 200 | Everyone grew: table 57,980, owner 2,899 | Only this owner grew: table 6,699, owner 2,899 |
|---|---|---|---|---|
| `dashboard?days=90` | 5.8 ms | 15.3 ms (2.6×) | 28.7 ms (**5.0×**) | 15.0 ms (2.6×) |
| `dashboard?days=7` | 5.0 ms | 11.5 ms (2.3×) | 26.4 ms (5.3×) | 14.5 ms (2.9×) |
| `dashboard-scores?days=90` | 2.3 ms | 1.9 ms | 6.3 ms (2.8×) | 6.9 ms (3.0×) |
| `questionnaire-list` | 3.2 ms | 3.0 ms | 3.7 ms | 3.2 ms |
| `battery-list` | 5.0 ms | 4.6 ms | 4.9 ms | 5.8 ms |
| `questionnaire-type-list` | 1.2 ms | 1.1 ms | 1.2 ms | 1.1 ms |
| `questionnaire-detail` | 1.2 ms | 1.1 ms | 1.1 ms | 1.1 ms |

The 5× matches the sandbox: in `load-20261102T052551Z`, at a constant 215 req/s, `dashboard` went
from 9 to 47 ms and Postgres rows read from 94k/s to 1.4M/s. Time inside Django rose from 0.8 to
1.8 s/s, and the dashboard's share of it from 17 % to 38 %.

- **Cause:** two of the dashboard's 8 queries sequentially scan all of
  `questionnaires_questionnaire`, ~58,000 rows to answer for an owner with 2,899: the per-type
  counts (`by_qtype`, owner only in a `FILTER`) and the per-battery counts (`battery_rows`, no
  owner on the questionnaire side). Together they take ~11 ms of the ~29 ms.
- **One owner's cost depends on everyone's data.** An owner whose own rows did not change still
  slowed 2.6×.
- **A shorter window does not help:** `days=7` costs about the same as `days=90`.
- **Lists are not affected;** pagination bounds them.
- **`dashboard-scores` grows differently:** it returns every submitted row of a type, so its
  response went from 17 KB to 187 KB. Its cost follows the owner's rows, not the table.

Candidate fix, tested as SQL only (no code changed) at table 57,980, owner 2,899, median of 25.
Both variants return identical rows:

| Query | Live | Owner on the questionnaire side of the join |
|---|---|---|
| `battery_rows` | 6.52 ms (full table scan) | 1.16 ms |
| `by_qtype` | 4.91 ms (full table scan) | 1.00 ms |

That saves ~9 ms of ~29 ms and should remove the dependence on other owners' rows. The rest grows
with the owner's own rows (the other queries, and Python over every row, ~9 ms), so the dashboard
would still slow as one owner's data grows.

## Not yet proven

That fixing the dashboard moves the knee. These tests need a re-stress on the sandbox:

1. Scope both queries to the owner, then re-stress from reset data.
2. Set `preAllocatedVUs` equal to `maxVUs` in `stress.js`, so logins happen up front and cannot
   feed the break.
