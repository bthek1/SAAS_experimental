# Load-test baseline: 2026-11-17, ceiling with owners logged in before the ramp (`LOGIN=setup`)

Plan: #50. Code: `0895c62` (.NET `instances`, FastAPI `catalog`), working tree clean. Each run started from
`just loadtest-reset`.

**Summary.** With k6's login burst removed, the .NET ceiling is **~1,387 req/s mixed and ~1,525 read**, about 5 %
and 11 % above the `LOGIN=vu` knees of 2026-11-14 (~1,315 and ~1,378). So the login burst was how those runs
ended, not what limited them: it is set off by a latency rise, and the latency rise comes at nearly the same rate
either way. **What limits them now is CPU time on the host, not the database or `instances`' own cores.** At each
break, Postgres answered `instances`' queries as fast as at half the rate (p95 under 10 ms, 0 to 5 active
connections), and `instances` used ~57 to 62 % of its 2 cores with no cgroup throttling. Yet its .NET thread pool
had work queued, and its tasks, and saas-db's, spent a growing share of each second waiting for a CPU. That
points at the Proxmox host's cores being shared with other guests, which this deploy cannot see or control.
Neither run failed a request.

## Deploy

As [2026-11-14-instances-dotnet.md](2026-11-14-instances-dotnet.md): 20 owners × 200 questionnaires, `instances`
on .NET (Kestrel, Npgsql pool 20) and `catalog` on FastAPI, 2 + 2 cores, saas-db 2 cores. The only change is k6's
`LOGIN=setup`: `setup()` logs each of the 20 owners in once, and the VUs share those sessions.

## Ceiling search

`just k6 stress TARGET=lxc STEP=20 STEP_TIME=1m START_RATE=500 MAX_RATE=1500 LOGIN=setup MIX=<mix>`, the
2026-11-14 ceiling search's command plus `LOGIN=setup`. Both runs exited 99 on k6's `dropped_iterations` limit.

| Run | Mix | Last clean minute | Slowest group p95 | `instances` CPU | saas-db CPU | `catalog` CPU | Host load (run mean) | Requests | Failed |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `stress-20261117T051903Z` | mixed | 19 at **~1,387 req/s** | 56 ms | 57 % | 61 % | 8 % | 12.3 | 1,405,479 | 0 |
| `stress-20261117T054059Z` | read | 46 at **~1,525 req/s** | 72 ms | 62 % | 54 % | 18 % | 8.2 | 2,974,601 | 0 |

Against `LOGIN=vu` (2026-11-14, same command otherwise): mixed ~1,315 at minute 17, read ~1,378 at minute 39.

- **No login burst.** All 20 logins ran in `setup()`. `catalog` stayed at 8 to 9 % CPU in the mixed run, and
  rose only with the read mix's type-list reads.
- **What ended each run.** Every endpoint group slowed together, writes most: in the mixed run's minute 20,
  `battery-create` p95 went from 19 ms (minute 12) to 384 ms and `questionnaire-detail` from 7 to 132 ms, the
  server-side p95 rising with them. k6 then ran out of VUs and dropped iterations (759 that minute).
- **The read run held its knee 27 minutes longer** than the mixed one, at a higher rate, with less host load (8.2
  against 12.3 on average). The two are not a controlled comparison of the mixes.

## Where the time goes at the break

Prometheus, per minute, `instances` unless named:

| | mixed min 12 (~1,166 req/s) | mixed min 20 (break) | read min 30 (~1,175) | read min 47 (break) |
|---|---:|---:|---:|---:|
| DB query p95 | 9.5 ms | 9.9 ms | 9.5 ms | 9.7 ms |
| Postgres active connections (`instancesdb`) | 1 | 5 | 1 | 0 |
| Thread-pool queue, max | 4 | 14 | 10 | 13 |
| Thread-pool threads, max | 4 | 4 | 4 | 4 |
| CPU pressure, waiting s/s: saas-instances | 0.49 | 0.62 | 0.49 | 0.62 |
| CPU pressure, waiting s/s: saas-db | 0.32 | 0.74 | 0.28 | 0.56 |
| cgroup throttling, any container | 0 | 0 | 0 | 0 |
| Host load (1 min) | 10.6 | 14.5 | 10.6 | 14.6 |

- **The database is not the limit.** Query latency is flat across the knee, and few connections are active. The
  2026-11-14 note that saas-db would break next (from its CPU rising per step) does not hold: its CPU rose, but its
  queries did not slow.
- **`instances` is not out of its own CPU.** It used ~1.1 to 1.2 of its 2 cores and was never throttled. Work
  queued on its thread pool, and the pool did not add threads past 4, which is what .NET's hill climbing does when
  more threads do not raise throughput.
- **Its tasks wait for a CPU.** `node_pressure_cpu_waiting_seconds_total` is per container here (saas-cache read
  0.008 s/s at the same time), and rose on saas-instances and saas-db toward each break. A container waiting for
  CPU below its own limit is competing with work outside it. The host has 24 cores, and its load was 7.8 before
  the mixed run began, with this deploy idle, so other guests were busy throughout.
- **Not proven:** which host cores each container ran on, and what else ran on them. That needs the Proxmox host
  (`pct config 246`, `mpstat -P ALL` during a run), which this session could not reach.

## How far to trust it

- **One run per mix.** The gains over `LOGIN=vu` (+72 and +147 req/s) are within the ~140 req/s that identical
  stress runs have varied by, so read them as "about the same", not as a measured improvement.
- **Host load was not controlled**, and differed between the two runs.
- **`LOGIN=setup` does not exercise logins.** Real users log in; these knees say nothing about a login burst.

## Still open

- **Confirm the host contention** on the Proxmox host during a run, or rerun with the other guests stopped. If it
  holds, this deploy's ceiling is a property of the shared host, and further code or pool tuning will not move it.
- **`dotnet_min_threads`**: a higher thread-pool minimum is the one `instances` knob that acts on a queued pool. A
  `load` at a fixed rate near the knee, with and without it, would show whether it helps or only adds contention.
