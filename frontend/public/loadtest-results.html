At matching rates

k6 p95 per endpoint in ms, since run start, so an earlier stall inflates the read-off column. Only the first three endpoints are cached: the others speed up because Postgres is less busy.

  • Most of the gain is less Postgres contention. The dashboards caused most of the rows read, and Postgres now reads 7 to 14 times fewer rows at matching rates.
  • Almost all of it comes from the dashboards. The type-list and PDF caches passed their gates by small margins. A PDF hit is ~35 times faster (2.9 ms against 101 ms), but p95 barely moves (113 to 105 ms), and k6 redownloads far more often than real users are likely to.
  • The read-mostly knee with the cache may be higher. That run ended on a stall while mean latency was about 10 ms.

When Redis fails

Both tests ran at ~110 req/s of read-mostly traffic. The cache fails open: no request failed in either.

What happens as data grows

A soak at a constant ~350 req/s with the cache on. The respondent flow adds about 8,000 questionnaires a minute. The first run fell off a cliff at about 236,000 rows (~12,000 per owner): saas-app ran out of CPU, k6 dropped 7,074 iterations after startup, and it was stopped at minute 35. After the dashboard fixes, the same command held the rate to minute 44, about 355,000 rows, with nothing dropped after startup. No request failed in either run.

What the dashboard fixes did

Four changes, deployed together, so k6 can't separate them: a 500-row limit on the points in dashboard/scores/, the median found in the database, the owner on the battery join, and two partial indexes. The biggest effect is on rows per owner. Peak capacity isn't shown to have moved. The same stress test on the same code reached ~430, ~497 and ~573 req/s, against ~480 before, so run-to-run variation is bigger than any gain it could show. Mean latency is usually lower at matching rates, most clearly at the top: 32 ms before at ~480 req/s, against 16 and 7 ms after.

Profile of a cache miss

A throwaway Postgres on the dev host, so read these as ratios. 300,000 questionnaires, the owner has 15,000, cache off. Median of 3 alternating rounds.

  • The profile confirms the likely causes. Parsing the timestamps the median loaded was the largest Python cost of a summary miss, and a scores hit cost as much as a miss because it unpickled and rendered the whole body.
  • A stale-statistics trap is gone. With stale planner statistics, the battery query scanned every owner's rows: 73.7 ms, against 5.3 ms with the owner on the join. With normal statistics both take 4.3 ms.
  • The indexes cost little. A submit-style update went from about 0.266 to 0.277 ms per row.

Holding a steady rate

The same 10-minute hold, before and after. Runs add rows, so latency drifts upward during a hold. The cache cuts that drift but doesn't remove it, because a miss still pays for the full query. The earlier run also used sync workers, so this isn't a pure cache comparison.

Still open

  • Find the next limit. The last soak was stopped at minute 45, so run one until it gives out.
  • Explain the variation. The same test on the same code ended at ~430, ~497 and ~573 req/s, and the same 15-minute soak held saas-app at 78 % in one run and 60 % in the other. Brief stalls well under the knee, and sudden collapses with CPU to spare, are part of it. They aren't from the cache, as the worst was with it off. Something below the app is suspected but not confirmed. Until this is understood, a single knee can't prove a gain under about 100 req/s.
  • Make a cache miss cheaper. On the deploy it still takes 124 to 179 ms at about 18,000 rows per owner, and low-traffic owners rarely get a hit. A scores miss still reads every row in the window for its totals.
  • Make saas-app cheaper per request, or give it more cores. It is still the busiest container.
  • Pre-allocate k6's VUs. New VUs log in during a slowdown, which may feed the break and make the knee partly a test artefact.

How this was measured

  • Deploy: unprivileged LXC containers on one Proxmox host. saas-app has 2 cores and 2 GB, saas-db 2 cores and 1 GB (Postgres 16), and k6 runs from its own container. saas-cache (1 core, 512 MB, Redis 7) was added for the cache runs.
  • Data: every measured run starts from just loadtest-reset: 20 owners × 200 questionnaires. Runs add rows, so only runs with the same settings compare cleanly.
  • Mixed traffic: 50 % owner reads, 30 % respondent flow, 15 % battery create, 5 % health check. Read-mostly is MIX=read.
  • Stress: the rate rises every minute until p95 passes 1 s, failures pass 1 %, or k6 drops 1,000 iterations. Slowest group is the worst p95 among the endpoint groups.
  • Dropped iterations: every soak drops some in its first 30 seconds (417 to 1,050) while k6's users log in. These are left out of drop counts "after startup".
  • Latency: before 4 November, k6 reported p95 calculated from the start of each run. Each minute's mean could still be recovered from its running totals, so charts show means for every run. Newer runs send histograms, which also give true per-minute p95.
  • Sources: the write-ups in loadtest/baselines/, per-minute figures from just k6-report <testid>. This page is updated by hand when a baseline is added.
